# 搭伙小灶：M1 改版设计

日期：2026-10-23
状态：待用户审阅
基础文档：`2026-10-22-pixel-kitchen-design.md`。本文没有提到的内容，仍按基础文档执行；两份文档有冲突的地方，以本文为准。

标记说明：没有标记的内容都是用户自己定的；**【我定的】** 是我替用户做的默认决定；**【留给实现者】** 是实现时自行决定的部分。

---

## 1. 为什么要改

M1 上线后，用户自己试用了一遍，反馈了四个问题：
1. **用起来不顺手**。录完食材看不到结果，以为没存上，又录了一次，结果数据表里鸡蛋、蛋炒饭都存成了两份。
2. **没有采购页**。按原计划，采购页要到 M3 才做。
3. **页面之间缺少一条主线**。几个页面各管各的，看不出谁先谁后、彼此有什么关系。
4. **用起来卡顿**。实测服务器每次响应只要 0.2–0.45 秒，慢的是网页前端：每次刷新整页都会闪一下，点了按钮没有任何反应，打开网页时也没有缓存。

另外，用户确认了两件事：**这个工具没有「厨师」这个角色**，而且名字改成「**搭伙小灶**」。

## 2. 核心变化

### 2.1 没有角色，所有人平等
- 不再区分厨师和吃饭的人。每个成员都能提要求、接要求，也都能看和改菜谱、采购清单、食材库。
- **直接注册**：打开网址，填名字和 4 位口令就能使用，不需要邀请码，也不需要谁来审批。
- **【我定的】注册上限 6 人**，满了就关闭注册。因为仓库是公开的，网址可能被陌生人找到，上限能限制被乱注册的范围。这个数字是配置项，以后可以调整。
- 用户要「先做两个人的」，所以第一版按两个人的使用场景来验收。

### 2.2 「要求」替代「点菜订单」
用户描述的流程是：「先发 request，然后看缺什么补什么。」

- **提要求**：任何人都可以提：「我想吃红烧肉，今晚，3 个人」。可以一次点好几道菜，可以写备注；时间按基础文档的结构化格式填（日期 + 餐次，具体几点可选填）。
- **我自己来做**：提要求时可以勾选「我自己来做」，提交后这个要求直接算作自己接下。这样就覆盖了「自己决定今天做什么」的情况，不用另开一套流程。
- **算缺料**：要求一提交，系统就对照食材库算出缺什么，加进采购清单，并在每一项上**标注是哪道菜、哪一天要用**。缺料的计算规则沿用 M1 已经实现的那套（按人数换算份量、扣掉其他未完成要求预留的量、单位对不上就打标记）。
- **接要求**：任何人都可以接，接了就由他来做。
- **状态流转**：
  - 待接 →（有人接）→ 已接 →（接的人点「做好了」）→ 做好了；
  - 接的人可以点「**做不了**」，要求回到「待接」，等别人接；
  - 提要求的人在「做好了」之前都可以**取消**，取消时这个要求带进采购清单的量会退回；
  - 其他状态之间的跳转一律拒绝（沿用 M1 防重复点击的规则）。
- **做好了**：由接的人点，按菜谱扣库存，规则和 M1 一样。
- 「点过几次」改成「做过几次」，只统计状态是「做好了」的要求。

### 2.3 推送（PushPlus）
| 什么时候 | 推给谁 | 内容 |
|---|---|---|
| 有人提了新要求 | 除提要求的人以外的所有成员 | 谁想吃什么、几个人、哪天哪一顿、备注，**以及缺什么、已加进采购清单** |
| 有人接了 | 提要求的人（如果接的是自己就不推） | 谁接了你的哪道菜 |
| 接的人做不了 | 提要求的人 | 谁做不了，要求重新等人接 |
| 做好了 | 提要求的人（自己做给自己就不推） | 菜名出锅啦，是谁做的 |
| 做完扣库存后，某样食材快用完了 | 接的人 | 某样快用完了，已加进采购清单 |
| 测试推送 | 自己 | 推送设置成功 |
| 每日早报（M4） | 所有设置了推送的人 | 今日菜单，附上快过期的食材 |

### 2.4 菜谱不再分两个区
- **【我定的】** 之所以把菜谱分成「拿手菜」和「想吃清单」，是因为原来只有厨师能加拿手菜。现在大家平等，这个划分就没必要了：所有菜谱都放在一起，谁都能加、能改、能删。「想吃某道菜」就直接提一个要求。
- M2 导入菜谱时，导入的结果直接存进菜谱，不再进想吃清单。

## 3. 页面结构（所有人一样）

底部导航：**今天 / 菜谱 / 采购 / 食材 / 我的**。样稿见 `.superpowers/brainstorm/32938-1792690936/content/structure.html`。样稿是按「厨师」画的，现在去掉了角色，所以第一个页面改成下面这样：

- **今天**
  - 最上面是「＋ 提个要求」按钮：选菜 → 几个人、哪天、哪一顿、具体时间（可选）、备注 →「我自己来做」开关 → 提交；
  - **我接的**：每条显示缺不缺料（缺料的点一下跳到采购）、「做好了」「做不了」两个按钮；
  - **等人接**：别人提的要求带「接下」按钮；自己提的要求带「取消」按钮；
  - **别人在做**：只看状态，自己提的那条可以取消；
  - **提醒**：快过期的食材（保质期 ≤ 3 天）、快用完的食材。
- **菜谱**
  - 最上面是「＋ 新菜谱」，点开后在底部弹层里填：菜名、几人份、食材（一行一样）、步骤；
  - 列表里每道菜显示：做过几次、缺什么，以及「想吃这道」按钮（点了直接打开提要求的弹层，并预先选好这道菜）；
  - 点菜名打开详情：食材按人数换算后的用量、步骤，以及「改」和「删」。
- **采购**
  - 「要买」：每一项标注是哪道菜、哪一天要用，或者是「快用完了」「手动加的」；
  - 打勾时弹出小框：买了多少、单位、保质期（可选），点「存进食材库」；
  - 「已买」：点一下可以撤销；
  - 最上面有「＋ 手动加」，手动加的项目可以删掉。
- **食材**
  - 最上面是「＋ 加食材」，在弹层里填；
  - 列表里新加的那一项排在最前面，并闪一下提示；主料显示数量和一条余量条，调料显示「有 / 快没了 / 没了」，点一下就能切换；
  - 点任意一样打开编辑弹层，可以改数量、单位、提醒值、保质期，也可以删除。
- **我的**：名字、推送设置（三步教程 +「发一条试试」）、退出登录。M4 再加我的要求记录、徽章和排行榜。

## 4. 交互规则（为了解决「看不到」和「卡顿」）
1. **先显示结果，后台再确认**：点下去立刻在界面上显示变化（新项出现、状态改变）。如果服务器返回失败，就把界面改回原样，并用一句中文说明原因。
2. **请求处理中按钮不可点**，防止连点导致重复。
3. **只有第一次打开时显示加载画面**。之后刷新时保留原来的内容，只在角落里显示一个小小的「同步中」。
4. **打开时先显示上次的数据**：上一次的数据存在本机，打开网页立刻显示出来，后台同时去取最新的。
5. **所有录入都放在底部弹层里**：存好后弹层关闭，弹出一句提示，同时在列表里高亮刚刚改动的那一项。
6. **不允许重名**：食材和菜谱都不能重名。如果录入了已有的名字，就提示「已经有「鸡蛋」了，要改数量就点它」，并且直接打开那一项的编辑弹层。

## 5. 视觉
- 名字改成「**搭伙小灶**」。**【我定的】** 副标题用「一起开小灶」。
- 风格不变，仍然是 A · 暖木农舍：配色、像素框、格子棚、像素字体都按基础文档。

## 6. 对后面几个里程碑的影响
- **M2 导入菜谱**：任何人都能导入，导入后直接存进菜谱，不再分区。
- **M3 采购和小票**：采购页的基础功能提前到这次改版里做（M3.5）；小票识别仍然放在 M3。
- **M4 统计和徽章**：去掉「厨师统计」，统计信息所有人都能看。「掌勺一百道」改成按「接下并做好了」的次数，人人都能拿；「夜宵达人」「第一口」等徽章按提要求的人计算。

## 7. 新的里程碑顺序
- **M1.5 改版**（下一步）：去掉角色并开放直接注册，要求的完整流程，五个页面，交互规则，采购页的基础功能，改名。验收时两个人用真机走完整条线：提要求 → 算缺料 → 推送 → 采购打勾入库 → 接要求 → 做好了扣库存。
- 之后依次是 M2 菜谱导入、M3 小票识别，M4 不变。

## 9. 补充规则（【我定的】，实现者自查时补上的）
- 如果要求已经有人接了，提要求的人又取消了，就推送给接的人：「xx 取消了 红烧肉」。
- 菜谱和食材的「删除」都是隐藏，不是真删。已经提过的要求、做过的统计里照样保留菜名。正在进行中的要求不受删除影响。
- 自己提的要求，自己之后也可以接，效果等同于提的时候勾了「我自己来做」。
