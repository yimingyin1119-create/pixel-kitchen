## 1. 要做什么，为什么做

用户和一个会做饭的朋友（下文叫「厨师」）经常一起吃饭，偶尔还有其他朋友来蹭饭。现在的情况是：
- 菜谱散在下厨房、小红书、抖音上，想吃的时候找不到；
- 厨师要记住谁爱吃什么，家里还剩什么，该买什么，全靠脑子记。

这个工具要把整件事串成一个闭环：**把菜谱收进来 → 点菜 → 厨师收到通知 → 做好以后自动扣库存 → 缺什么自动进采购清单 → 买回来入库**。同时它要好玩：像素风画面，记录每道菜点了多少次，有徽章和排行榜，让人愿意天天打开。

### 怎样算成功
- 两三个人日常真的在用，点菜不用再在微信上发文字；
- 厨师不用另外记账，库存和采购清单基本可信；
- 录入一份菜谱比手抄还省事。

### 目标
- 在微信里打开就能用的像素风网页，可以加到手机桌面；
- 第一版就把下面第 4 节的所有功能做齐（用户选了「全部一起做」）；
- **要放进作品集**（2026-10-22 用户确认），对 n8n 部分有这些要求：
  - 打开 n8n 画布，一眼就能看懂每条自动化流程在做什么。「导入菜谱」「小票入库」「每日早报」「通知中心（新订单 / 接单拒单 / 出锅 / 缺料提醒）」这几条要拆成独立、节点清楚的流程；
  - 节点用中文命名，关键位置放便签（Sticky Note）说明这一步在干什么；
  - 登录校验做成一个子流程，由各个流程复用；
  - 容易算错的计算部分（扣库存、单位换算、徽章等）仍然放在代码模块里，保证测试得到；
  - 最后要交付工作流截图和一张架构图，用来放进作品集。

### 不做的事
- 不做真正的微信小程序（不注册、不审核、不备案）；
- 不做支付和金额结算；
- 不支持多个厨师、多个厨房，也不开放给陌生人注册；
- 不算营养和卡路里。

### 反目标（功能都能跑，但出现下面这些情况也算失败）
- 录菜谱比手写还麻烦，或者 AI 拆出来的东西错到每次都要大改；
- 库存数字越用越乱，厨师不再相信它；
- 推送多到让人想屏蔽；
- 看起来像一个普通的后台管理表格，失去了像素风那种温暖感。

## 2. 使用者和权限

| 角色 | 是谁 | 能做什么 |
|---|---|---|
| 厨师 | 用户的朋友，只有 1 个 | 所有功能：管理菜谱、接单或拒单、标记做好、管理食材库和采购清单、排每日 menu、查看统计 |
| 吃饭的人 | 用户本人，加上其他朋友 | 看菜谱、点菜、把链接或截图加进「想吃清单」、看自己的点菜记录、排行榜和徽章、设置自己的推送 |

- **【我定的】** 登录方式：每个人有一个名字加一个简单口令（比如 4 位数字），由厨师在后台创建账号。不做注册流程。
- **【我定的】** 吃饭的人底部导航只显示「点菜 / 菜谱 / 我的」；厨师会多看到「采购 / 食材库」。

## 3. 技术形态和约束

- **形态**：H5 网页，在微信内置浏览器里打开，需要兼容 iOS 和 Android 的微信 WebView，拍照和上传图片在微信里必须能用。
- **后端**：用 n8n。前端的每一个操作都对应一个 n8n webhook 工作流。定时任务（每天早上推送 menu）也放在 n8n 里。
- **部署（2026-10-22 修订）**：用户和厨师住对门，用户也说不准 Mac 平时是不是合着的，所以**第一天就把 n8n 部署到云服务器上**，不再走「先在 Mac 上跑 + 免费隧道」这条路。原因是隧道地址每次重启都会变，厨师手机桌面上的图标和分享链接会跟着失效。
  - 服务器：每月 4 到 5 欧的欧洲 VPS（比如 Hetzner），由用户自己购买，助手不经手付款。在上面用 Docker 跑 `n8nio/n8n:2.44.6`，前面挂一个 Caddy 自动申请 HTTPS 证书。
  - **【我定的】** 域名默认用 sslip.io 这类免费通配域名（例如 `1-2-3-4.sslip.io`）。如果申请证书遇到限制，再请用户买一个便宜域名（每年 10 欧左右）。
  - 对公网只开放 `/webhook/pk/*`；n8n 编辑器不对外，用户通过 SSH 端口转发在自己电脑上打开。
  - 用户的 Mac（Apple Silicon，没装 Homebrew，npm 全局目录在 `~/.npm-global`）只用来开发和跑测试。
  - **【我定的】** 前端放在 GitHub Pages 上（用户已经有 GitHub Pages 的使用经验），后端地址是固定的，在构建时写死。
- **并发**：n8n 默认会同时处理多个请求。现在的写法是「读出全部数据 → 计算 → 整行写回」，两个请求同时到达时，后写的会覆盖先写的（比如库存数字被改错）。所以生产环境要设置 `N8N_CONCURRENCY_PRODUCTION_LIMIT=1`，让请求排队处理。代价是有人导入菜谱时，别人点菜可能要多等十几秒，这个可以接受。
- **执行记录**：n8n 默认会保存每次执行的完整输入，里面有口令、登录凭证和照片。所以主接口、导入、小票这几个工作流都不保存成功的执行记录，失败的记录只保留 7 天（`EXECUTIONS_DATA_PRUNE=true`、`EXECUTIONS_DATA_MAX_AGE=168`）。
- **备份**：每天自动备份一次 n8n 数据库，在服务器上保留 14 份；用户 Mac 上的脚本把备份拉到 iCloud 文件夹。备份绝不能放进 GitHub 仓库，因为仓库是公开的。
- **AI**：**【我定的】** 用 Claude Haiku 5.5，因为它能看图，价格也便宜，用户预充 5 美元就能用很久。零成本的备选是 Google Gemini 的免费额度。用户目前还没有任何 API key，实现计划里要包含一步步带用户注册、充值、拿 key 的说明。API key 只能放在 n8n 里，不能出现在前端。
- **微信推送**：用 PushPlus。**【我定的】** 每个人在「我的」页面里填写自己的 PushPlus token。
- **用户所在地**：荷兰。超市是 Albert Heijn 和亚洲超市，小票是荷兰语，食材库里统一用中文名。
- **安全**：webhook 暴露在公网上，所以每个请求都要校验登录身份，不能让知道地址的人随便调用。
- **预算**：越低越好，服务器加 AI 每月控制在几欧以内。

## 4. 功能

### 4.1 菜谱库（分两个区）
- **拿手菜**：可以直接点。只有厨师能把菜加进这个区。
- **想吃清单**：谁都能往里加（贴链接或上传截图）。不能直接点，但是 **【我定的】** 每个人可以点「想吃 +1」。厨师学会以后，一键把它升级成拿手菜。
- 每份菜谱的字段：菜名、图片、来源链接、基准份数（几人份）、食材列表（名称、用量、单位、主料还是调料）、步骤、标签。

### 4.2 菜谱导入
所有导入方式都先生成一份**草稿**，由导入的人确认或修改后才正式入库。
1. **贴链接**：支持下厨房和一般的网页。n8n 抓取页面内容，交给 AI 拆成上面那些字段。
2. **小红书 / 抖音：以截图为主（2026-10-22 修订）**。服务器在荷兰，又没有登录，抓小红书多半只会拿到登录页；而且很多小红书菜谱本来就写在几张图片里。所以识别到小红书或抖音链接、或者分享文案时，**直接引导用户上传截图**，同时把分享文案一起交给 AI 作为补充。抓取只作为顺手一试，不作为主路径。
   - 抖音的视频菜谱，内容主要在视频的配音里，截图和文案都很难还原，所以**不承诺能识别**。界面上要如实告诉用户。
3. **拍照或截图识别**：拍菜谱书、截菜谱图都行，**一次最多 6 张图**，AI 把几张图合起来整理成一份菜谱。
- AI 拆食材时，要尽量把食材名对应到食材库里已有的名字（比如「西红柿」和「番茄」算同一样），单位也尽量对应到食材库里用的单位。对应不上的在草稿里标出来，让人确认。

### 4.3 点菜
- 像购物车一样，一单可以点好几道菜（只能选拿手菜）；
- 每单可以填：备注（「少辣」「不要香菜」）、几个人吃，以及想吃的时间。想吃的时间**必须是结构化的**（2026-10-22 修订）：选日期，再选餐次「午饭 / 晚饭 / 夜宵」，也可以再选一个具体时间点；不能是随手写的文字。因为夜宵徽章、厨师按顿排单、早报都要依靠这个时间来计算；
- 下单时，按「人数 ÷ 基准份数」换算每样食材的需要量，再和库存对比。缺的食材在订单上标出来，同时加进采购清单（注明是因为哪一单）；
- 订单状态：待接单 → 已接单 → 已做好；另外还有「已拒单」（厨师可以写原因，比如缺料），以及「已取消」（点菜的人在接单之前可以取消）。

### 4.4 推送（PushPlus → 微信）
| 什么时候 | 推给谁 | 内容 |
|---|---|---|
| 有新订单 | 厨师 | 谁点了什么、几个人吃、什么时候吃、备注、缺哪些料 |
| 接单 / 拒单 | 点菜的人 | 接了，或者拒了加上原因 |
| 做好了 | 点菜的人 | 「红烧肉出锅啦」之类 |
| 每天早上 | **【我定的】** 所有人；厨师那份额外附上快过期的食材 | 今日 menu |

**【我定的】** 早上推送的时间先定 9:00，后面可以改。

### 4.5 食材库
- 字段：名称、主料还是调料、数量、单位、低库存阈值、保质期（选填）、入库日期。
- 厨师点「做好了」时，按菜谱用量乘以份数换算，自动扣减库存。
- **【我定的】** 菜谱里没有具体数量的食材（比如「盐 适量」）不自动扣，靠厨师手动把状态改成「快没了」或「没了」。
- 数量低于阈值时，自动加进采购清单。
- 厨师随时可以手动修改数量。

### 4.6 采购清单
- 来源有三种：缺料自动加入、低库存自动加入、手动添加。同一样食材合并成一条。
- 买到一样勾一样；勾选时填买到的数量（默认是需要量），然后自动入库。
- **拍小票入库**：拍一张超市小票（荷兰语）→ AI 识别出商品和数量 → 对应到采购清单里的条目和食材库里的名字 → 厨师确认 → 自动勾选并入库。对应不上的商品，让厨师选择「新建食材」或者「忽略」。

### 4.7 每日 menu
- 厨师可以从拿手菜里手动挑今天要做的菜；
- 系统推荐：只推荐用现有库存就能做出来的菜，优先用掉快过期的食材。具体推荐逻辑【留给实现者】，可以用 AI，也可以写规则，或者两者结合；
- 首页最上方显示今日 menu（见样稿）。

### 4.8 点菜次数和游戏化
- 每道菜上显示「点过 N 次」，菜单可以按热度排序；
- 个人排行榜：每个人最爱吃的前 5 道菜；
- 像素成就和徽章，比如「红烧肉老顾客」（同一道菜点 10 次）、「尝遍 20 道菜」、「第一个吃到新菜」。徽章的具体清单【留给实现者】，但第一版至少要有 6 到 8 个；
- 厨师统计：最受欢迎的菜、超过 30 天没人点的菜、每个人的口味偏好；
- **【我定的】** 点菜次数在厨师点「做好了」之后才加 1，算的是真正吃到的，拒单和取消不算。

## 8. 里程碑顺序（2026-10-22 修订，属于必须执行的要求）
功能还是一次全部做完，但要按下面的顺序搭建。**每个里程碑都要在真手机的微信里验证过，才能进入下一个**。目的是尽早发现那些会推翻整个方案的问题：
1. **M1 点菜闭环**：登录 → 点一道菜 → 厨师微信收到推送 → 厨师点「做好了」→ 库存被扣减。要用真机验证三件事：微信里打开 GitHub Pages 页面能正常调用服务器、PushPlus 推送真的能送到、页面字体正常显示；
2. **M2 菜谱导入**：贴链接、多图截图，以及小红书、抖音的引导流程；
3. **M3 库存、采购和小票**；
4. **M4 每日 menu、推荐、徽章、排行榜、统计和早报**，以及作品集材料。
